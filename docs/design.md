# Keel Design

Status: draft, milestone 1 scope. Owner: Simon.

## Problem and goals

AI agents run for minutes or hours and make many LLM calls and tool calls. In most agent code today, if the process crashes partway through, the work is lost. Restarting means paying for every LLM call again, and worse, it can repeat actions that already happened in the real world, such as sending an email or making a payment twice.

Keel is a Python library that makes agent runs durable. Every step is recorded in a Postgres step log, so a crashed run resumes from where it stopped instead of starting over.

**Core guarantee:** a run survives crashes, completed steps are never executed again, and a tool that is not marked idempotent never executes twice.

## Non-goals (milestone 1)

- Multiple workers, leases, and heartbeats (milestone 2)
- Redis, queues, and scheduling (milestone 2)
- Sleeps or timers as steps
- Human-in-the-loop approvals and the `needs_review` state
- Agent code catching and recovering from step errors (a step that fails after retries fails the run)
- Concurrent steps within a run (for example `asyncio.gather`), which need a deterministic numbering scheme
- Moving large payloads to object storage
- A web UI or hosted service
- Support for every LLM provider (a mock provider is enough for milestone 1)

## Glossary

- **Run:** one execution of an agent from start to finish, identified by a unique ID. A run is always in one of these states: `pending`, `running`, `completed`, `failed`, `cancelled`.
- **Step:** a single LLM call or tool call made by an agent. A step is Keel's unit of durability. Ordinary code between steps is not a step.
- **Step log:** the Postgres record of every step in a run. Each step is written twice: a `started` record before it executes and a `completed` record with its result afterward.
- **Replay:** re-running an agent's code from the top after a crash. Steps that are already completed in the log return their recorded result instead of executing. Execution becomes live again at the first step without a completed record.
- **Side effect:** a change in the outside world caused by a tool, such as sending an email, charging a card, or writing a file. Side effects are why repeating a step can be harmful.
- **Idempotent tool:** a tool that is safe to run more than once with the same idempotency key, because the result is the same as running it once (for example a web search, or an API that deduplicates by key).
- **Idempotency key:** a unique key generated by the runtime for each step and saved in the step's `started` record before execution. It is the same on every retry of that step. It is never generated by the LLM.
- **Uncertain step:** a step with a `started` record but no `completed` record after a crash. Keel cannot know whether its side effect happened.
- **Poison pill:** a step that crashes the process every time it runs. Without a shared attempt limit, it would cause an endless crash and restart loop.
- **Non-determinism error:** the error raised when replayed code calls a different step than the log recorded at that position.

## Programming model

Agents and tools are async Python functions registered with decorators.

```python
import keel

@keel.tool(idempotent=True)
async def search_web(query: str) -> list[str]:
    ...

@keel.tool()  # non-idempotent by default
async def send_email(to: str, body: str, *, idempotency_key: str) -> None:
    # pass the key to the email provider so it can deduplicate
    ...

@keel.agent
async def research_agent(topic: str) -> str:
    plan = await keel.llm(prompt=f"Plan research on {topic}")
    results = await search_web(plan)
    summary = await keel.llm(prompt=f"Summarize: {results}")
    await send_email(to="me@example.com", body=summary)
    return summary
```

Rules:

- Tools are non-idempotent unless marked `idempotent=True`.
- A tool that declares a keyword-only `idempotency_key` parameter receives the step's key from the runtime.
- Agent code must be deterministic between steps. Anything random, time-based, or network-based must happen inside a step.
- Step inputs and results are canonicalized (dict keys sorted the same way on the live and replay paths), because Postgres `JSONB` does not preserve key order.
- Steps run one at a time. Step errors cannot be caught by agent code to continue the run.
- LLM calls are treated as idempotent: retrying one costs money but has no side effects.

## Data model

All data lives in Postgres for milestone 1. `input` and `result` columns are `JSONB`.

**`runs`**

| Column | Notes |
|---|---|
| `id` | primary key |
| `agent_name` | which agent definition the run uses |
| `status` | `pending`, `running`, `completed`, `failed`, `cancelled` |
| `input` | JSONB, what the run was started with |
| `result` | JSONB, final output once completed |
| `failure_reason` | why the run failed |
| `created_at`, `updated_at` | timestamps |

**`steps`**

| Column | Notes |
|---|---|
| `run_id` | foreign key to `runs.id` |
| `step_number` | 1, 2, 3, and so on within the run |
| `kind` | `llm` or `tool` |
| `name` | tool name, or model name for LLM calls |
| `idempotency_key` | generated by the runtime when the step starts |
| `status` | `started`, `completed`, `failed` |
| `attempts` | number of attempts so far |
| `input` | JSONB, what was sent |
| `input_hash` | hash of the canonicalized input, compared on replay |
| `result` | JSONB, what came back |
| `started_at`, `completed_at` | timestamps |

`(run_id, step_number)` is unique, so the database itself rejects a duplicate step.

## Execution and replay

**Run lifecycle:**

- A new run is created in `pending`.
- The runtime moves it to `running` when it starts executing the run, before the first step.
- Calling `run` with an existing run ID resumes that run instead of creating a new one.
- `resume_all()` resumes every run in `running`. A restarted process calls it on startup to pick up runs interrupted by a crash.

**Executing a step (normal flow):**

1. Look up the step log entry for `(run_id, step_number)`.
2. If no entry exists, write a `started` record with a new idempotency key, execute the step, then update the record to `completed` with the result.
3. If a `completed` entry exists, check that its `kind`, `name`, and `input_hash` match the call. If they match, return the recorded result without executing. If they don't, fail the run with a non-determinism error.
4. If a `started` entry exists without completion, the step is uncertain (see Side effects and idempotency).

**Fewer steps on replay:** if the agent finishes while the log still holds steps it never reached, the code has changed. The run fails with a non-determinism error.

**One executor per run in a process:** the runtime refuses to start a run that is already executing in the same process. Enforcement across processes comes from leases in milestone 2.

**Retries on errors:**

- Temporary errors (timeouts, rate limits, 5xx responses) are retried. Permanent errors (bad input, authentication failures) fail the step immediately.
- Default: 3 attempts total, exponential backoff with jitter (about 1s, 2s, 4s).
- Retry settings are configurable per tool.
- Every retry of a step reuses that step's idempotency key.
- `attempts` is incremented and saved before each attempt executes, so an attempt interrupted by a crash still counts.
- The attempt limit is shared across crashes, not reset on resume. A step that crashes the process every time it runs (a "poison pill") fails after the limit instead of looping forever.
- A step is marked `failed` when it hits a permanent error or exhausts its attempts. The run is then marked `failed`.

**Cancellation:** a step already in progress finishes and its result is logged. No new steps start after that, and the run is marked `cancelled`.

## Leases and heartbeats

Not needed in milestone 1, which runs in a single process. To be designed in milestone 2, based on these ideas:

- A worker claims a run with a lease that expires unless renewed by heartbeat.
- A lease with a timeout is not safe alone, because a paused worker can wake up after its lease expired. Each lease grant gets an increasing fencing token, and step log writes carrying an older token are rejected.

## Side effects and idempotency

When an uncertain step is found after a crash:

- **Idempotent tool or LLM call:** retry it with the same idempotency key.
- **Non-idempotent tool:** do not retry. Mark the run `failed` with a reason naming the uncertain step, so a human can check whether the side effect happened.

Because the idempotency key is generated and saved before execution, a retry can never produce a different key. This avoids the failure described in the ACRFence paper, where an LLM regenerates a new reference ID on retry and a payment goes through twice.

## Failure scenarios

| Scenario | What happens | Mechanism |
|---|---|---|
| Crash between steps | Resume, replay completed steps, continue live | Step log, replay |
| Crash during an LLM call | Retry the call | LLM calls treated as idempotent |
| Crash during an idempotent tool | Retry with the same key | Idempotency key |
| Crash during a non-idempotent tool | Run fails, flagged for a human | Uncertain step detection |
| Code changed between crash and resume | Run fails with non-determinism error | Position, kind, name, and input hash check |
| Dict key order differs after reading from JSONB | Same steps matched correctly | Canonicalized inputs |
| Tool returns a temporary error | Retried with backoff, then run fails | Retry policy |
| Tool returns a permanent error | Step fails immediately, run fails | Retry policy |
| Run cancelled mid-step | Step finishes, no new steps start | Cancellation rule |
| Step crashes the process every attempt | Fails after 3 attempts total | Attempt limit shared across crashes |
| Postgres briefly unreachable | Open question | |

## Invariants

1. A completed step is never executed again. On replay, its recorded result is returned.
2. A non-idempotent tool executes at most once per step, even across crashes.
3. An idempotent tool may execute more than once, but always with the same idempotency key for that step.
4. Idempotency keys are generated by the runtime and saved before execution, never generated by the LLM.
5. Every step has a `started` record before it executes.
6. Steps within a run are numbered 1, 2, 3, and so on, with no gaps or duplicates.
7. On replay, if the code calls a step whose kind, name, or input differs from what the log recorded at that position, or finishes before reaching every logged step, the run fails with a non-determinism error.
8. A run in `completed`, `failed`, or `cancelled` never executes another step.
9. A run has at most one active executor at a time. (Enforced within a process in milestone 1; across processes by leases in milestone 2.)
10. When a run is cancelled, a step already in progress finishes and is logged, and no new step starts.

## Testing strategy

- **Mock LLM provider:** scripted responses, random latency, and simulated 429 errors, so tests are free and deterministic.
- **Counting fake tools:** tools that record how many times they actually execute, used to check invariants 1 through 3.
- **Crash recovery test (milestone 1 definition of done):** start a run, `kill -9` the process at a random step, restart it, and assert the run completes with every non-idempotent tool executed exactly once.
- **Non-determinism test:** change the agent's step order between crash and resume, and assert the run fails with a non-determinism error.
- **Uncertain step test:** kill the process inside a non-idempotent tool, and assert the run fails with a reason naming that step.
- Each invariant should map to at least one test.

## Milestones

1. **Durable single process:** step log, replay, retries, uncertain step handling. Done when the `kill -9` test passes.
2. **Distributed workers:** Redis queue, multiple workers, leases, heartbeats, fencing tokens.
3. **LLM gateway:** rate limiting, cost tracking, budgets, real provider support.
4. **Long-running features:** `needs_review` state, sleeps, human approvals, parent and child runs.
5. **Chaos and observability:** random worker kills under load, OpenTelemetry GenAI tracing, MCP tools.
6. **Speculative execution:** run predicted next steps early for safe steps, then train a speculator on logged runs.

## Open questions

- How should Keel behave if Postgres is briefly unreachable mid-step?
- When should large inputs and results move from Postgres to object storage?
- Replaying full history vs. snapshotting state for very long runs.
- How will the `needs_review` state let a human resume a run after confirming a side effect?
